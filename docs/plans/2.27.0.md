# 2.27.0 plan

Status: plan only. Nothing here is implemented. Implementation starts when the owner says so.

Scope: the six open issues of milestone 2.27.0: #649, #651, #652, #653, #655, #656. #654 (2.28.0 code review) was read
for overlap only (see "Overlap with #654").

## Rules every chunk follows

1. **Per-site integration.** Each site's signal is integrated from the spectrum (reflectance × illuminant, or the scene's
   spectral radiance) against that site's channel response when the site is read, on every render path. A cache may hold
   geometry (scene points, field factors, PSF kernels), material indices and spectra (spectral radiance at the nodes). A
   cache may not hold a value in which a channel response has been summed over the spectrum for a material or a signal
   level, and neutral materials take no shortcut through a white integral. Each design below says what its caches hold.
2. **Speed against accuracy.** Where a faster method differs from the full method by more than the equivalence tolerance
   (below), both are kept, the choice is `fast` (docs/API_STYLE.md, "Exact and fast modes"), the fast method is the default
   for the display view and sRGB samples, and the full method is the default for DNG, JPEG and PNG exports,
   `simulateIdealReference` and `fast: false`. No existing default changes without an owner decision.
3. **One path where the results are the same.** Where a faster method gives the full method's result within the
   equivalence tolerance, only the faster method is kept: no flag and no registry entry. Each new method below states
   which case it is and the test that proves it.
4. **Equivalence tolerance** (the one `test/display-view-defocus-regrouped.test.ts` already uses for two methods that
   form the same sum): every site's expected electrons within 1e-9 relative, and 8-bit samples within one code. GPU
   against CPU keeps its own rule: every value inside the a-priori bound the result reports (docs/WEBGPU.md, "Error
   bounds"). Accuracy bounds against the capture stay as documented in docs/DISPLAY_VIEW.md.
5. Regions and parts stay byte-identical to the whole view on the same path, and results stay deterministic (fixed
   tiles at absolute positions, seeded draws).
6. New code that a default capture or view does not need loads on demand. No bundle size limit of
   `test/capture-bundle.test.ts` is raised by a chunk; a chunk that cannot fit stops and reports.
7. Evidence (AGENTS.md rule 1): every speed claim is a before/after measurement with the command, and every model has a
   cited free source.

## Measurements

All baselines below were measured for this plan on November 17, 2026: `main` at `94f56f3` (2.26.0), `npm run build`,
Node 26.13.1, Apple M5 Pro (18 cores), macOS. One Node process per case, at most three at a time,
`prepareDisplayView(request, { gpu: "off" })` then one `render`. The machine was under heavy load from other work (load
average 74–200), so the figure is the **CPU time of the process for the one render** (`process.cpuUsage`, user + system),
an upper bound; ratios are the measure. Profiles are `node --cpu-prof`, self time.

## #649 Faster display view with lens corrections and sharpening

### Current behavior and baseline

Case: `lens: { catalogue: "pv-50-1.2-pro", fNumber: 8 }`, view 1500 × 1000, one 96 × 96 part at (702, 452) (exact area
mean, 16 real pixels per display pixel).

| Request | CPU time | Against plain |
| --- | --- | --- |
| No corrections | 1.26 s | 1 |
| `output.lensCorrections` (distortion, lateral color, vignetting; 3 passes) | 3.26 s | 2.6× |
| `output.sharpening: { radiusPixels: 1, amount: 1 }` | 2.75 s | 2.2× |
| Corrections and sharpening | 7.29 s | 5.8× |

The issue's figures (1.17 s, 2.74 s, 7.0 s) are reproduced.

### Root cause

`src/facade/display-view-detail.ts`:

- With lateral color the view renders three passes (one per channel map). Each pass calls `renderDisplayView` on its own,
  so each pass computes the expected electrons of the same sites again, and renders the same real pixels again. The
  profile of the corrected and sharpened part: 48 % in the lens signal's tap sums (`MaterialSums.slot`, `add`, `value`),
  8 % in `kernelSite`: site signals, not the corrections.
- With sharpening, `passes()` runs twice: once at the view's size and once at 1:1 over the region and the mask's reach.
  That is six renders with lateral color. The view-size passes of the red and blue maps are then discarded: every
  component's expected value is overwritten by the area mean of the sharpened 1:1 values, and only the first pass's
  covariance and counts are used.
- A real pixel's rendered value under the fast method does not depend on the channel map: the gain is taken at the
  developed pixel's center. Only the rectangle each display pixel reads differs between the passes.

### Design

All three steps give the current values (same operations on the same operands), so they are case 3 of the rules: one
path, no flag. Proof: the existing `test/display-view-lens-corrections.test.ts` values unchanged, plus a new test that
the samples, expected values and noise of each case equal the 2.26.0 results byte for byte (recorded hashes of the
current build for the four requests above at 8×, 2× and 1:1).

1. **Skip the discarded passes.** With sharpening, the view-size render runs for the first channel map only (covariance,
   counts, highlight statistics). Saves two of six renders with lateral color.
2. **One site store for the call.** `renderDisplayViewDetail` wraps `setup.signal` in a store that keeps each native
   site's expected electrons for the duration of the one call (fixed 64 × 64 tiles keyed by absolute site, a byte budget,
   least recently used first). Every pass and the 1:1 render read it. What it holds: the value of
   `signal.site(x, y)` for that site, the integral the site itself formed when first read. It is keyed by the site's
   coordinates only, never by material, channel or level, and it is dropped when the call returns.
3. **One rendered-pixel record for the fast passes.** The renderer's per-real-pixel memo (#392, `MEMO_SIZE` terms per
   real pixel) is kept across the passes of one call when the fast method runs (`DisplayViewSetup` gains an optional
   `pixelStore`; `renderDisplayView` reads and fills it where it fills its own memo today). The exact method
   (`fast: false`) keeps its memos off, as now.

CPU only. The GPU keeps reporting `unsupported-on-backend` for these options (unchanged); a GPU path for corrections
would follow chunk G1 and is not planned here.

No new fast method is proposed for sharpening. The 1:1 render is needed for the mask (the display-scale mask was measured
in 2.25.0 and left out), and after steps 1–3 its cost on a view at or below 25 real pixels per display pixel is the
store's reads plus the mask. For coarser views (the stratified estimator) the 1:1 render still follows the real pixels;
that is recorded as a known cost, not changed.

### API changes

None public. Internal: `DisplayViewSetup.pixelStore?`, a site store factory in `display-view-detail.ts`.

### Files

`src/facade/display-view-detail.ts`, `src/facade/display-view.ts` (the memo hook only),
`test/display-view-lens-corrections.test.ts`, new `test/display-view-detail-shared.test.ts`, docs/DISPLAY_VIEW.md
("Lens corrections and sharpening", cost paragraph).

### Risks

- The memo's records include terms that depend on the pass (the display pixel's weights): only the per-real-pixel terms
  may be shared. The byte-for-byte test is the guard.
- Memory: the site store and the pixel store are bounded (32 MiB each by default) and per call.

### Acceptance

- Bytes equal to 2.26.0 on the recorded cases; regions equal the whole view.
- On the case above: corrections ≤ 1.5× the plain part (3.26 s → ≤ 1.9 s), corrections and sharpening ≤ 2.6× (7.29 s →
  ≤ 3.3 s), sharpening alone ≤ 1.7× (2.75 s → ≤ 2.1 s). These are targets from the pass count (6 renders → 2 with shared
  sites); the chunk reports what it measures.

### Effort

M (one agent session). Chunk P3.

## #651 Display view: camera rotation with a rolling shutter and defocus on the CPU

### Current behavior and baseline

Case: `lens: { prime: 50, fNumber: 8 }`, `subjectDistanceM: 0.63`, `exposure: { mode: "manual", iso: 100,
shutterSeconds: 1/125 }`, view 1194 × 796 (stratified, 5.03 real pixels per display pixel per axis), region at
(501, 334). Rotation is `motion: { angularVelocityRadPerSec: { yaw: 0.0766 }, shutter }`; defocus is
`lens.defocus: { model: "geometric-disc" }` with `lens.focusDistanceM` 0.8 × the subject distance (disc radius 11 sites).

| Request | Region | CPU time |
| --- | --- | --- |
| No motion, in focus | 48 × 32 | 0.26 s |
| Rotation, rolling, in focus | 48 × 32 | 0.51 s |
| Rotation, rolling, out of focus | 48 × 32 | 19.96 s (39× the in-focus rolling case) |
| Rotation, rolling, out of focus | 24 × 16 | 5.75 s |
| Rotation, **global**, out of focus | 24 × 16 | 2.40 s |
| No motion, out of focus (regrouped, #612) | 24 × 16 | 0.43 s |

The issue's region (192 × 128, 16 times the 48 × 32 one) extrapolates to about 320 s on this chart; the issue measured
900 s on its own chart. The global-shutter row shows the same cost class: the issue's note that the global shutter is not
affected does not hold for a disc of this size.

### Root cause

`src/facade/display-view-lens-signal.ts`, `kernelSite`:

- Rotation puts the request on the lens signal. There, a disc of up to 64 sites radius is summed tap by tap:
  (2R + 1)² taps × T temporal midpoints × the spectral nodes per site (529 × 8 × 20 here), through the per-material sums.
  The regrouped defocus (#612, in-focus signal, then the disc by runs) exists on this path only above 64 sites
  (`createLargeLensSignal`), and that path is refused with a rolling shutter.
- With a rolling shutter each row has its own instants, so the lattice cache (tagged with the instant) is reused along a
  row and not across rows: every tap of a new row is mapped through the rotation and looked up in the chart again.
  Profile of the 24 × 16 case: 42 % per-material sums, 20 % chart lookups, 16 % rotation and mapping, 11 % `kernelSite`
  and `lattice`.

### Design

Three steps. μ below is a site's expected electrons, E_c(x; t) channel c's in-focus expected electrons at site position x
with the scene read at instant t, D the disc.

1. **Global shutter, any radius: the regrouped path with a cost choice** (same sum regrouped; case 3, no flag beyond
   the existing `lens.defocus/view-regrouped` switch it already follows). `createLargeLensSignal` is used below 64 sites
   too when its operation count is lower, by the rule of `regroupedDefocusCheaper` extended with the midpoint count. A
   small region keeps the tap sum. Proof: per-site electrons within 1e-9 relative of the tap sum and samples within one
   code, on the lens cases of `test/display-view-lens.test.ts` out of focus (vignetting, distortion, rotation with 3 and
   8 midpoints) at R = 3, 11 and 40.
2. **Rolling shutter, full method: regrouped by rows** (same sum regrouped; case 3). For output row y with instants
   t_y,i: μ_c(x, y) = (1/T) Σ_i Σ_s D(s)·E_c((x, y) − s; t_y,i). The in-focus rows y − R … y + R are computed at row y's
   instants over fixed 128-column segments (so prefix sums start at fixed positions and regions equal the whole view),
   all three channels from one lookup per lattice point, then `convolveSiteKernelRuns` with a height of one row.
   Per site this costs (2R + 1)·T in-focus points and 2·(2R + 1)·T run reads, against (2R + 1)²·T taps of N nodes. It
   takes the same cost choice as step 1. The refusal above 64 sites stays, as in the capture. Proof: as step 1, against
   the current tap sum, on the #640 cases of `test/display-view-lens.test.ts`.
3. **Rolling shutter, fast method: row bands** (differs beyond the tolerance; case 2, flag and registry entry
   `motion.shutter.rolling/view-row-bands`, override the top-level `fast`). Rows are grouped into bands whose instants
   differ so little that the scene moves less than 1/16 site across the band (band height from the angular speed, the
   focal length, the pitch and the line skew; at least one row, at most 64). Every row of a band takes the band's
   middle row's instants, so a band is one global-shutter problem and uses step 1's tiles: T in-focus points per site
   instead of (2R + 1)·T. The full method is step 2. Error: a shift of at most 1/32 site of the in-focus image within a
   band, bounded by the image gradient; reported in the `view.defocus` assumption (`rollingBands: { rows, shiftSites }`).
   Go/no-go: against step 2 on the validation charts, expected values within 0.1 code RMS and 1 code at most; if it
   fails, the threshold is tightened or the method is dropped and step 2 is the only path.

Caches: in-focus rows and tiles hold per-site, per-channel electrons formed at that site and instant (the regrouped
sum's inner term, as `createLargeLensSignal` holds today), keyed by site position and instant; lattice tiles hold the
material index and field factor of a lattice point. None is keyed by material or level.

**A documented estimate.** `PreparedDisplayView` gains `estimateRender(view)`: the operation counts the render would
make (sites read, taps per site, temporal midpoints, the method each choice would take) without rendering. It returns
counts, not seconds; docs give the measured time per operation on one named machine as a guide. This answers the issue's
"so callers can decide before rendering".

GPU: requests with rotation stay on the CPU (`unsupported-on-backend`), as today. A GPU lens path is chunk G1 (#655);
rotation on it is not planned for 2.27.0.

### API changes

- New method `PreparedDisplayView.estimateRender(view)` and its result type (additive).
- New registry entry `motion.shutter.rolling/view-row-bands`; new fields in the `view.defocus` assumption.

### Files

`src/facade/display-view-lens-signal.ts`, new `src/facade/display-view-lens-regroup.ts` (loaded with the lens signal),
`test/display-view-lens.test.ts`, new `test/display-view-lens-regrouped.test.ts`; wiring in chunk I1.

### Risks

- Chart-boundary ties: the regrouped path reads the same lattice points as the tap sum, so ties resolve the same way;
  the tests include a Siemens star through the frame center.
- Memory of the row method: (2R + 1) rows × 3 channels × T instants of one segment at a time; bounded and released per
  row.
- The band threshold is a new approximation: see go/no-go.

### Acceptance

- Step 1: global, out of focus, 24 × 16: 2.40 s → ≤ 0.6 s; whole-view parity with the still out-of-focus case within 3×.
- Step 2 (`fast: false`): rolling, out of focus, 48 × 32: 19.96 s → ≤ 7 s (estimate: 23× fewer tap operations, but one
  mapped lookup per in-focus point).
- Step 3 (default): rolling, out of focus, 48 × 32: 19.96 s → ≤ 1.5 s, that is within 3× of the in-focus rolling case
  (0.51 s); the issue's 192 × 128 region within 3× of its in-focus time.

### Effort

L. Part of chunk P2 (steps 1–3) and I1 (the estimate and the flag).

## #652 Layered chart scenes

### Current behavior

One fronto-parallel plane at `subjectDistanceM`; defocus is one disc for the whole frame. There is no baseline to
measure: the feature is new. The reference costs are today's single-plane defocus (the tables of #651 and #653).

### Model

A scene of K opaque, fronto-parallel cards at distances d_1 < … < d_K and a back plane at d_B > d_K, seen through a thin
lens focused at `lens.focusDistanceM`. Geometric optics: the irradiance at image point x is the mean, over the aperture,
of the radiance of the first surface each ray meets,

  E(x, λ) ∝ ∫_A P(a; x) · L_first(x, a, λ) da / ∫_A P(a; x) da,

where the ray through aperture point a and image point x meets the plane at depth d at x_d + R_d·a (x_d the chief ray's
point, R_d the signed blur radius at that depth, c = f²·|s − d| / (N·d·(s − f)), `calculateDefocusCircle`), and P is the
aperture function (the disc; blades, spherical aberration and the cat's eye of `lens.defocus`; a catalogue lens's bokeh).
This is the thin-lens camera of distributed ray tracing (Cook, Porter and Carpenter, "Distributed ray tracing", SIGGRAPH
1984; Pharr, Jakob and Humphreys, *Physically Based Rendering*, 4th ed., §5.2.3, free online; survey: Barsky and Kosloff,
"Algorithms for rendering depth of field effects in computer graphics", 2008). It gives both occlusion directions: a
blurred front card spreads over the card behind it (rays that miss the front card continue), and a blurred background
is cut off at a sharp front edge (rays the front card blocks never reach it).

### Design

**Evaluation on the site lattice.** For layer k with disc kernel D_k (today's kernel: exact cell areas,
`createDefocusDiscSiteKernel`, or the shaped kernel), tap t of the kernel stands for the aperture cell around
a = t / R_k. The site's spectral radiance is

  S(x)[n] = Σ_k Σ_t D_k(t) · V_k(x, t) · F · L_k(x − t)[n],

with V_k(x, t) the visible fraction of that aperture cell at layer k: the share of its sub-samples whose rays pass every
nearer card (a rectangle test per nearer card, since cards are axis-aligned rectangles) and, for the back plane, every
card. The site's electrons are Σ_n A_c[n]·S(x)[n], formed at the site with its own channel response; with
`lens.diffraction` each node's diffraction kernel is applied to S first (the existing "diffraction convolved with the
disc" approximation, per layer).

- A site whose aperture cone meets one layer only (no card edge within its blur) has V = 1 on that layer and 0
  elsewhere: its value is today's single-plane sum for that layer, bit for bit. Those sites take the existing paths
  (tables, regrouped runs), one prepared signal per layer.
- Sites within a blur radius of a card edge take the sum above ("edge sites").
- **Fast and full** (differ beyond the tolerance; case 2, registry entry `scene.layers/occlusion-samples`): the
  visible fraction from 4 × 4 sub-samples per aperture cell (fast) or 16 × 16 (full). Proof of the gap and of each
  bound: the energy test below.
- A single-card scene with no back plane lights is routed to the existing single-plane path: identical bytes.

**Point lights on the back plane.** Each light is a small emitter with a position (seeded grid with jitter), a spectrum
(an engine illuminant or a blackbody) and a luminous intensity. A light contributes to site x through the one aperture
point a* that joins them, a* = (p_light − x_B) / R_B: its spectral contribution is its intensity spectrum times
P(a*; x) / (aperture area in sites²) times the visibility of a* past the cards, averaged over the site's aperture nodes
(the pixel-aperture box). So a light renders as the aperture shape at the back plane's blur size, cut by nearer cards,
with the cat's eye toward the frame's edges where P includes it. In focus (|R_B| below half a site) a light's energy
goes to the site that holds it. Validity: the emitter's image is at most one site across; larger emitters are refused
(use a card). The contribution is spectral and is integrated against the site's channel response at the site.

**The cat's eye in the view.** Today the view refuses `lens.defocus.catsEye` (the kernel varies over the field). In the
layered sum the aperture function is evaluated per site, so layered scenes render it in the view as the capture does. The
single-plane refusal is unchanged.

**Render paths.** One module holds the sum (`layered-scene-signal.ts`), used by:

- the display view: a `DisplayViewExpectedSignal` for layered scenes (edge sites) over per-layer signals (other sites);
- the capture and the ideal reference: a planar radiance provider (`layered-scene-provider.ts`) that evaluates the same
  sum at the environment chain's query points, so capture and view agree per site within 1e-9 relative, as for the other
  lens options.

GPU: a layered scene runs the CPU reference labeled `unsupported-on-backend` in 2.27.0 (owner decision 5).

Caches: per layer, the existing tables and tiles; for edge sites, spectral lattice tiles (chunk S0) holding S per
lattice point (spectral radiance at the nodes, no response). Nothing is keyed by material or level.

### API changes (additive)

```ts
scene: {
  kind: "layered-chart";
  cards: { distanceM: number; centerU: number; centerV: number; width: number; height: number;
           scene: ChartScene; depthLabel?: boolean }[];          // frame units, as seen from the lens
  backPlane?: { distanceM: number; reflectance?: ChartReflectance;
                pointLights?: { seed: number; columns: number; rows: number; jitter?: number;
                                luminousIntensityCandela: number; spectrum?: CaptureIlluminant } };
}
resolveLayeredChartPreset({ scale: "macro" | "tabletop" | "large", cards?: number, focusDistanceM, lens })  // staircase layout
```

- `result.scene.layers`: per card and for the back plane, `{ distanceM, defocusDiameterSites, withinDepthOfField }`
  (from `calculateDepthOfField` at the request's circle of confusion), so callers can label them.
- Staircase preset: each card steps back and sideways and overlaps the one behind it. Depth steps grow geometrically away
  from the focus plane (ratio 1.5 by default), symmetric in defocus, so more cards sit where sharpness changes fastest.
  Scales: macro (first step 1 mm), tabletop (1 cm at about 1 m), large (0.25 m at about 5 m). The spacing is owner
  decision 5.
- Refused with layered scenes in 2.27.0: `motion` of any kind, `lens.projection` other than rectilinear, a card that
  is not opaque, disc radii above 64 sites on edge sites.

### Files

New: `src/facade/layered-chart-scene.ts` (schema, validation, presets, depth report),
`src/facade/layered-scene-signal.ts`, `src/facade/layered-scene-provider.ts`, `test/layered-scene-*.test.ts`,
`docs/LAYERED_SCENES.md`. Wiring (scene parsing, result fields, refusals, registry) in chunk I2:
`src/facade/simulate-capture.ts`, `src/facade/simulate-display-view.ts`, `src/facade/fast-methods.ts`, `src/index.ts`.

### Risks

- Energy at occlusion edges: each layer's kernel has its own lattice, so the visible fractions of two layers do not sum
  to exactly one. The energy test bounds it; if the fast bound cannot be met with 4 × 4 sub-samples the count rises.
- Seams between edge sites and other sites: both use the same per-layer kernels, so there is none by construction; a
  test checks continuity across the classification boundary.
- Scope: this is the largest item of the milestone. It can ship without holding the others.

### Tests (the issue's four, plus two)

1. A single-card scene equals today's single-plane render byte for byte.
2. A slanted edge on each card: the edge-spread width matches the disc of `calculateDefocusCircle` at that depth within
   the lattice bound of docs/DISPLAY_VIEW.md ("Defocus", analytic validation).
3. Occlusion edges against an independent reference: a brute-force aperture integration in the test (64 × 64 aperture
   points per site, plain JavaScript, no engine kernels), for a front edge over a far card and a far edge behind a
   blurred front card. Full within 0.5 % of the local swing; fast within 2 %.
4. Capture and view agree per site within 1e-9 relative; the box-downsized capture against the view within the
   slanted-edge thresholds (0.6 code RMS, 3 at most).
5. Energy: uniform white cards at several depths over a white back plane render flat within 0.2 % (full) and 1 % (fast).
6. A point light: its disc diameter equals the back plane's defocus circle, its summed electrons equal the in-focus
   light's within 1e-9 relative when no card cuts it, and a card edge cuts it on the correct side for a back plane behind
   the focus plane and (with a card as the far surface) in front of it.

Benchmarks: the tabletop preset at f/2 and f/8, capture region and view part, fast and full, with the share of edge
sites; reported, with no threshold in CI.

### Effort

XL (three to four agent sessions): P5 (core, parallel) and I2 (wiring, serial).

## #653 Quality chart renders: defocused and long-lens frames

### Current behavior and baseline

Case: Quality options (`lens.diffraction: "circular-aperture"`, the four-spot filter, the 2 × 2 box, AHD), view
768 × 512 (7.8 real pixels per display pixel per axis, stratified), `exposure` manual ISO 100. One band of 768 × 43
display pixels (a twelfth of the frame) at y = 213.

| Frame | CPU time, one band | Profile |
| --- | --- | --- |
| 50 mm f/2, focus 0.8 × the subject distance (disc radius 13, diffraction radius 1) | 36.05 s | 69 % `inFocusTile`, 14 % renderer |
| 50 mm f/2, focus 1.25 × (disc radius 11) | 35.91 s | the same shape |
| 200 mm f/8, in focus | 7.86 s | 41 % `tapsValue`, 18 % renderer |

A band of 768 × 4 pixels of the first frame costs 6.26 s, a sixth of the 43-row band for a tenth of its rows.

### Root cause

1. **The in-focus tiles do the spectral work once per channel.** The regrouped defocus (`prepareLargeKernel`,
   `inFocusTile` in `src/facade/expected-signal.ts`) computes all three channels' in-focus signal at every site of a
   tile, each channel with its own pass over the taps and nodes. The tap kernels differ between channels only by the
   channel response, which does not depend on the tap.
2. **No uniform shortcut in the tiles.** A site whose whole window reads one material still sums every tap. On this
   chart 57–67 % of tile sites are such sites.
3. **Whole tiles for a few rows.** The run convolution works in fixed 128-site output tiles over fixed 64-site in-focus
   tiles. A band or region pays for whole tiles above and below it, and a render of the next band (a separate prepared
   view or process) pays for the shared tile rows again. This is the "work repeated across bands".
4. **In focus, the tap sum is at its floor for its grouping.** Each site sums 4 lattice groups of 10 × 10 taps at 20
   nodes for its one channel. Two exact rearrangements of that loop were prototyped and gave nothing: flat spectra
   storage (5.30 s against 4.90 s) and merging runs of equal materials with prefix kernels (1.54 taps per run; 4.89 s
   against 4.90 s).

#642's choice (`regroupedDefocusCheaper`) is right for these sizes: both defocused frames take the regrouped path, and
the 4-row band shows why its model charges 192 sites of widening. Step 3 below removes that charge, and the model is
updated with it.

### Design

All steps form the same sums in another order: case 3, one path, no flag. Proof for each: per-site electrons within
1e-9 relative of 2.26.0's and samples within one code on `test/display-view-defocus-regrouped.test.ts`'s cases plus the
three frames above; regions equal the whole view.

1. **Channel-free tile sums.** For each tile site, S[n] = Σ_t K′(t, n)·L_m(t)[n] once (K′ the tap kernel per node without
   the response, from `input.kernels` and the offset weights), then the three channels as E_c = Σ_n A_c[n]·S[n]. One pass
   over taps and nodes instead of three. S is spectral radiance at the site; the response is applied at the site.
   Prototype: 768 × 4 band 6.26 s → 4.22 s, samples identical.
2. **Uniform windows in the tiles.** A site whose window reads one material takes Σ_n L_m[n]·(Σ_t K′(t, n)) and the three
   responses, with the window test from summed-area tables of material changes per tile (as the filled band does), not a
   scan. Prototype (with a scan): 4.22 s → 3.07 s; the 768 × 43 band 36.05 s → 15.21 s with steps 1 and 2, samples
   identical (2.4×).
3. **Rows on demand.** Output tiles and in-focus tiles keep their fixed origins, and compute only the rows a render
   reads (a row bitmap per tile; `convolveSiteKernelRuns` already takes a row pattern, and each output row depends on its
   own source rows and on prefix sums that start at the tile's fixed left edge, so a row's bits do not depend on which
   other rows exist). A band then costs its rows plus 2R, and neighboring bands stop paying for each other's tile rows.
   `regroupedDefocusCheaper` drops its 192-site widening accordingly, so smaller regions take the regrouped path.
   Estimate for the 43-row band: 384–512 tile rows → 359 rows read, 1.1–1.4×; for the 4-row band about 3×.
4. **In focus: pre-integrated spectral radiance per lattice point.** μ = Σ_n A_c[n] Σ_t K_n(t)·B(x − t)[n] with
   B(p)[n] = Σ_o w_o·L_m(p + o)[n] over the query offsets (box nodes and filter spots): 81 taps of a spectral value
   instead of 400 taps of a material, B kept in spectral lattice tiles (chunk S0). Prototype with a simple ring: a
   192 × 16 region of the 200 mm frame 2.23 s → 2.04 s CPU, 1.74 s → 1.38 s wall, samples identical. The gain is small
   here because most of this frame's time is outside the tap sum; it is kept because the lens path needs the same
   regrouping (#655) and it is larger there.

Kernel construction is already cached per prepared view and by content (`EXPECTED_SIGNAL_TABLE_CACHE_SIZE`, #446); the
profiles show no kernel construction above 1 %. No change.

CPU only. The GPU's Quality passes already render these frames up to a 64-site disc.

## #655 Catalogue-lens display view: GPU, or a much faster CPU path

### Current behavior and baseline

Case: the fast defaults, `lens: { catalogue: "pv-50-1.2-pro", fNumber: 8 }` against `lens: { prime: 50, fNumber: 8 }`,
whole views (stratified).

| View | Pixel aperture | Prime | Catalogue | Ratio |
| --- | --- | --- | --- | --- |
| 192 × 128 | point | 3.87 s | 58.74 s | 15× |
| 96 × 64 | point | 2.57 s | 41.60 s | 16× |
| 96 × 64 | 2 × 2 box | 3.43 s | 127.61 s | 37× |

Profile of the 96 × 64 catalogue view (kernel radius 4, 2,752 field zones, all read):

| Share | Where |
| --- | --- |
| 31 % | per-material sums of the taps (`MaterialSums.add`, `slot`, `value`) |
| 20 % | `buildTables` per field zone |
| 17 % | `calculateInverseRadialSourcePointValue` (the distortion's inverse, by bisection to the last bit, per lattice point) |
| 11 % | `kernelSite` |
| 21 % | the rest (renderer, lookups, PSF interpolation) |

### Root cause

1. `createDisplayViewLensPsf().tables` calls `buildTables` for every zone, and `buildTables` copies every material's
   spectrum each time (thousands of materials for a dead-leaves element) before it builds the zone's kernels.
2. The lens path still forms per-material sums; #643's per-tap sum was added to the rectilinear path only.
3. With the box aperture every lattice group is summed tap by tap: 4 groups of (2R + 2)² taps where one kernel pass over
   pre-integrated radiance would do.
4. Each lattice point's distortion inverse is a bisection to adjacent doubles (up to 80 steps, about 53 in practice).
5. Zone PSF kernels are resolved again for every prepared view.
6. Nothing of this path runs on the GPU.

### Design, CPU

Steps 1–5 form the same sums or the same roots (case 3, no flag). Proof: per-site electrons within 1e-9 relative of
2.26.0's on `test/display-view-lens-catalogue.test.ts` and `test/display-view-lens-catalogue-zones*.test.ts`, samples
within one code, regions equal the whole view.

1. **Zone tables without the copies.** A zone builds only its kernels (`nodeKernels`: response × kernel per node, no
   material) and shares the view's frozen spectra. Bit-identical.
2. **Per-tap sum with the field factor**: Σ_t f_t·Σ_n L_m(t)[n]·C_c(t, n), added in tap order, as #643 does without a
   factor.
3. **Box aperture and filter spots pre-integrated**: B(p)[n] = Σ_o w_o·F(p + o)·L_m(p + o)[n] in spectral lattice tiles
   (chunk S0; spectral radiance times the field factor, no response), then one kernel pass per site,
   μ = Σ_n A_c[n] Σ_t K_n(t)·B(x − t)[n]: (2R + 1)² taps instead of G·(2R + 2)². This is the issue's "Related" point for
   the view: the box aperture then costs about what the point aperture does.
4. **A faster distortion inverse for the view.** Newton steps from the previous lattice point's root, then the same
   final bracket test as the bisection, falling back to the bisection when a step leaves the bracket. New file; the
   capture keeps `calculateInverseRadialSourcePointValue`. Proof: the root within 4 ULP of the bisection's over 10⁶
   radii for each of the 30 catalogue profiles, and the site test above.
5. **Zone PSF kernels kept across prepared views**, by content (lens id, f-number, focus, pitch, raster, nodes, zone
   count), least recently used, 32 MiB. Holds PSF kernels only: optics, no channel response, no scene.
6. **Uniform windows, fast method** (differs beyond the tolerance; case 2, registry entry
   `lens.catalogue/view-uniform-window`, override `lens.catalogue`'s `fast`). A site whose kernel window reads one
   material (summed-area test on the lattice tiles) takes Σ_n L_m[n]·(F₀·S_c[n] + ∇F·M_c[n]): the field factor expanded
   to first order about the site, with S_c and M_c the zone kernel's sums and first moments per node (kernel and
   response per node, no material). The full method sums every tap with its own factor (steps 2–3). Error: the factor's
   second-order change over the kernel's reach. Go/no-go: per-site difference from the full method ≤ 1e-6 relative on
   every catalogue lens at its widest and narrowest aperture; otherwise the method is dropped.

### Design, GPU (chunk G1)

Extend the Quality passes to the lens signal for chart and `material-layers` scenes with a still camera:

- Pass 1 (lattice materials) maps each lattice point through the lens in float32 (inverse radial distortion by a fixed
  number of Newton steps, the projection, the plane point) and stores the material, the field factor and an uncertainty
  flag when the point is within its position bound of a material boundary, as the composite module does today.
- Pass 2 (site moments) gathers the taps with the zone's kernels (uploaded per zone the band reads, per node, with the
  response; no material folded in) and each tap's field factor, per spectral node, then sums the nodes.
- Pass 3 is unchanged.
- The a-priori bound gains the mapping's terms (position error × the flagged-material rule; factor error as a relative
  term). Flagged pixels are recomputed on the host with the CPU reference, as today.
- Fast and full on the GPU are the CPU's zone method and one-zone-per-site method; the GPU runs the zone method only and
  `fast: false` with a catalogue lens stays on the CPU, labeled. The existing registry entry `prepareDisplayView.gpu`
  covers the GPU choice.

This is the issue's first option and the only one that can meet "a small multiple of the prime's time": after the CPU
steps the estimate is 5–6× the prime on one thread (below), because a catalogue site still reads 81 taps of 20 nodes
where a prime site reads one point.

### API changes

- New registry entry `lens.catalogue/view-uniform-window`; `view.lensPsf` assumption gains the method's fields.
- GPU: a catalogue-lens view may report `backend: "webgpu-f32"`; no option changes.

### Files

CPU: `src/facade/display-view-lens-signal.ts`, new `src/optics/radial-distortion-newton.ts`,
`test/display-view-lens-catalogue*.test.ts`, new `test/radial-distortion-newton.test.ts`. GPU: new
`src/gpu/display-view-lens-gpu.ts`, `src/gpu/wgsl-display-view-lens-kernel.ts`, and the seams in
`src/gpu/display-view-quality-gpu.ts`, `src/gpu/display-view-gpu-renderer.ts`, `src/facade/display-view-gpu.ts`
(`supports`), new `test/display-view-lens-gpu*.test.ts`, docs/WEBGPU.md, docs/WEBGPU_DEVICES.md.

### Risks

- GPU float32 positions near chart boundaries: more flagged pixels than the rectilinear path; the host recomputation
  could dominate on fine charts. Measured on hardware before the path is enabled by default for these requests.
- The Newton inverse can move a lattice point by a few ULP, which matters only for a point exactly on a material
  boundary; the tests include the star through the frame center (r = 0 is exact on both).
- Memory: spectral lattice tiles are 160 bytes per lattice point at 20 nodes; the store is bounded (64 MiB default).

### Acceptance

- CPU, steps 1–5 (`fast: false` and default): 96 × 64 point aperture 41.60 s → ≤ 25 s (estimate from the profile: 22 s);
  box aperture 127.61 s → ≤ 1.3× the point aperture's time.
- CPU, step 6 (default): 96 × 64 → ≤ 16 s (estimate: 15 s, 5.7× the prime).
- GPU: on the hardware of docs/WEBGPU_DEVICES.md, a catalogue-lens part within 3× the prime's GPU time, every value
  inside its bound, 0 conformance failures; SwiftShader conformance in CI.
- Output within the documented tolerance of the current CPU result in every case.

### Effort

CPU: L (chunk P2, with #651). GPU: XL (chunk G1, two to three sessions plus a hardware run by the owner).

## #656 CPU cost of the display view with develop options

### Current behavior and baseline

Case: `lens: { prime: 50, fNumber: 8 }`, view 1500 × 1000, one 96 × 96 part at (702, 452) (147,456 real pixels).
Standard is `STANDARD_LOOK` (`naka-rushton-luminance`), Recover is `highlightMode: "reconstruct"`, the push is
`exposureCompensationStops: 1`.

| Develop options | CPU time | Against none |
| --- | --- | --- |
| None | 0.40 s | 1 |
| Recover | 0.38 s | 1 |
| +1 stop | 0.28 s | 0.7 |
| Standard | 0.53 s | 1.3 |
| Standard and Recover | 0.62 s | 1.5 |
| Standard and +1 stop | 0.61 s | 1.5 |
| Recover and +1 stop | 1.76 s | 4.4 |
| Standard, Recover and +1 stop | 2.71 s | 6.7 |

The issue's pattern is reproduced: each option alone is cheap, Recover with the push is not.

### Root cause

`src/facade/display-view-rendering.ts`. With `reconstruct`, a real pixel whose camera channels come within 8.5σ of 0.8
of white takes the 3-D Gauss–Hermite rule over the whole development chain: 6 points per axis, 216 chain evaluations,
each with the highlight blend, the matrix, the luminance ratio (a portable `pow`) and their slopes. The push moves a
third of this part's pixels into that range: 50,758 of 147,456 real pixels ran the rule. The memo of #645 (results kept
by the exact bits of the pixel's moments) hit 85 times: it helps flat patches, not detail. Profile: 65 % in `render`,
`integrate`, `highlight` and `chain`; 10 % in the portable `log2`/`exp2`.

The tone curve's inputs are not recomputed per part: nothing in the profile is per-part setup. The cost is per pixel.

### Design

**An order-adaptive chain rule as the fast method** (changes the fast method's values; owner decision 1). Measured on the
case above with the rule's order fixed for every pixel, final 8-bit samples against the full rule (16 points):

| Points per axis | CPU time | Samples differing from the 16-point rule (of 27,648), all by one code |
| --- | --- | --- |
| 16 (full, `fast: false`) | 39.3 s | 0 |
| 6 (fast today) | 2.41 s | 12 |
| 4 | 1.11 s | 17 |
| 3 | 0.78 s | 20 |
| 2 | 0.74 s | 33 |

The fast method becomes: 3 points per axis (27 evaluations) where the pixel's channel standard deviations are all below
a threshold σ₀ and its ±8.5σ box crosses no kink of the chain other than those the 3-point rule is measured against;
otherwise 6 points as today. σ₀ is set from a sweep like the existing fast-against-full one (300 seeded means and
covariances, channel σ up to 0.076; docs/DISPLAY_VIEW.md, "Coupled rendering") so that the adaptive rule stays inside the
fast method's documented bounds against the full rule (chain 1.5·10⁻², and 2.4·10⁻⁴ for σ ≤ 0.01). The full method
(16 points) is unchanged. This is the existing registry entry `output.highlightMode.reconstruct/view-moments`; its
`fast` text and the `view.rendering` assumption (`chainPointsPerAxis: "3-or-6"`) change. No new flag.

Which case: the adaptive rule differs from today's fast rule beyond the equivalence tolerance (one code on about 0.1 %
of samples here), so it is not a silent replacement; it stays inside the documented fast-against-full bound. Proof:
`test/display-view-coupled-rendering.test.ts` extended with the sweep for the adaptive rule (same bounds as the fast
rule's), the Monte Carlo comparison (means within 1·10⁻³ plus four standard errors) and the downsized-capture comparison
(0.5–0.6 code plus three standard errors).

No same-value saving of note was found in the profile: the time is the number of chain evaluations, and each one is
already a few dozen operations plus one portable `pow`.

**GPU.** The coupled WGSL (`src/gpu/wgsl-display-view-coupled.ts`) takes the same adaptive order so GPU and CPU keep
agreeing inside the bound; its conformance cases are re-recorded against the CPU reference.

Not proposed: separating the tone curve from the reconstruct blend (the tone step by luminance conditioning after a 3-D
rule for the blend alone). It treats the blended values as normal, a new approximation whose error at the blend's kinks
is not known; it can be measured later if the adaptive rule is not enough. Also not proposed: any store of chain results
indexed by rounded channel levels (rule 1 and the 2.22.0 decision on level-indexed values).

### API changes

None in types. The fast method's values change within its documented bound (decision 1); the assumption text changes.

### Files

`src/facade/display-view-rendering.ts`, `src/gpu/wgsl-display-view-coupled.ts`,
`test/display-view-coupled-rendering.test.ts`, `test/display-view-coupled-gpu*.test.ts`, docs/DISPLAY_VIEW.md ("Coupled
rendering"), docs/WEBGPU.md ("Coupled rendering steps"). Registry text in chunk I1.

### Risks

- The kink test must be conservative; a missed kink would put a 3-point rule where the 6-point one is needed. The sweep
  includes pixels straddling 0.8 of white, white, and each channel's clip level.
- Hash locks of coupled-rendering views change and are re-recorded (the values move by at most the fast bound).

### Acceptance

- Standard, Recover and +1 stop: 2.71 s → ≤ 1.0 s (≤ 2.5× the part without develop options); Recover and +1 stop:
  1.76 s → ≤ 0.8 s.
- Every bound of "Coupled rendering" holds for the adaptive rule; the full rule's results are bit-identical to 2.26.0.

### Effort

M for the CPU, S for the WGSL. Chunk P4.

## Owner decisions

1. **#656: change the fast chain rule from 6 points per axis to 3-or-6.** This changes the default display view's
   values with `reconstruct` or the desaturation, inside the fast method's documented bound (measured: one 8-bit code

2. **Hash locks under equivalent regroupings.** P1 and P2 form the same sums in another order; a sample may move by one
   code at a rounding boundary. Recommendation: allow re-recording a hash lock when the equivalence helper passes for
   that case (prototypes gave identical samples everywhere measured).
3. **Confirm the equivalence tolerance** of rule 4 (1e-9 relative on expected electrons, 8-bit samples within one code)
   as the test for "one path, no flag". Recommendation: yes; it is the tolerance already used for #612 and #642.
4. **New fast methods that keep a full method and a flag** (they differ beyond the tolerance): rolling-shutter row bands
   (#651), catalogue uniform windows (#655), layered occlusion sub-samples (#652). Each defaults to fast for the display
   view and sRGB samples and to full for exports and `fast: false`. Two of them have a go/no-go measurement and may be
   dropped. Recommendation: approve as designed.
5. **#652's public shape:** the `layered-chart` scene, the preset spacing (geometric steps of ratio 1.5 from the focus
   plane; first steps 1 mm, 1 cm, 0.25 m), the cat's eye rendered in the view for layered scenes only, no GPU path in
   2.27.0, and the 2.27.0 refusals (motion, non-rectilinear projections). Recommendation: approve; revisit the spacing
   once the presets can be looked at.
6. **#655: where the GPU path lands.** The CPU steps reach an estimated 5–6× the prime, not "a small multiple".
   Recommendation: ship the CPU steps in 2.27.0, build G1 in parallel, and include it only if the hardware run passes;
   otherwise it moves to the next release and #655 stays open for it.
7. **#649's per-call site store.** It keeps each site's own integrated electrons, keyed by site coordinates, for one
   render call. Recommendation: confirm this is within rule 1 (it extends the lifetime of the renderer's existing site
